# TB-001 — Bitget BTC Telegram Executor

Status: BASELINE  
Owner: repository owner  
Target stage: DRY_RUN, then paper trading after acceptance  
Live trading: disabled

## 1. Outcome

Система получает торговые сигналы из двух заранее разрешенных приватных Telegram-каналов, детерминированно разбирает их, применяет локальную риск-политику, формирует и сопровождает намерения по сделкам BTCUSDT на Bitget USDT-фьючерсах и отправляет владельцу понятные уведомления. В DRY_RUN и paper-режимах ни один запрос не может создать реальный биржевой ордер.

## 2. In scope

- Только BTCUSDT, Bitget USDT-фьючерсы и cross margin.
- Два Telegram-источника: scalping и intraday; распределение капитала 15%/85%.
- Сигналы LONG/SHORT, диапазон или одиночная цена входа, stop under/above, лестница целей, перевод в безубыток и явный повторный вход.
- Лимитные заявки, докупка, частичная фиксация, отмена, сверка состояния и time stop.
- Личные Telegram-уведомления, приватные команды, последние 10 сделок с пагинацией и справка.
- DRY_RUN, replay/backtest, paper trading, журнал событий и статистика.

## 3. Out of scope

- Любые пары кроме BTCUSDT.
- Спотовая торговля, isolated margin и рыночные ордера.
- Самостоятельный подбор риска агентом или использование процента риска из текста сигнала.
- Мартингейл, автоматическое увеличение риска после убытка и автоматическое включение live trading.
- LLM в цепочке принятия решения о реальном ордере.

## 4. Actors and systems

| Actor/system | Responsibility | Trust boundary |
|---|---|---|
| Владелец | Утверждает риск, источники и переход между стадиями | Единственный субъект, разрешающий live |
| Telegram reader | Читает только allowlist каналов через существующую session | Вход недоверенный |
| Parser | Преобразует сообщение в типизированный `SignalCandidate` | Детерминированный код |
| Risk engine | Рассчитывает допустимый размер и отклоняет нарушение | Не зависит от текста риска в сигнале |
| Execution engine | Создает idempotent order intents и сверяет состояние | В live по умолчанию недоступен |
| Bitget adapter | Изолирует версию API, подпись и ответы биржи | Секреты только из runtime env/secret store |
| Telegram bot UI | Уведомляет владельца и принимает приватные команды | Доступ только allowlist user ID |

## 5. Inputs and data contracts

Обязательные поля валидного сигнала: источник, message ID, timestamp, BTCUSDT, направление, хотя бы одна цена/зона входа и stop rule. Цели могут уточняться последующим сообщением, но до получения обязательных полей торговое намерение не создается.

Parser распознает:

- LONG: `лонг`, `long`, маркер роста; SHORT: `шорт`, `short`, маркер снижения;
- вход `A-B` или одиночный уровень;
- `стоп под X` / `стоп над X` как границу, от которой применяется утвержденный технический offset;
- список целей и указание перевода stop в breakeven;
- `сигнал активен` как явный re-entry, связанный с исходным сигналом;
- текстовые `risk 0.5%`, `1%`, `1/2`, `1/3` как контент источника, не изменяющий локальный cap.

Идентификатор дедупликации: `source_channel_id + message_id + normalized_signal_revision`. Повторная доставка не создает второй setup.

Telegram-авторизация использует заранее созданный `.session`; интерактивный вход в production-процессе запрещен. Запуск reader не должен завершать другие пользовательские сессии.

## 6. Behavioral scenarios

### S-01 Валидный диапазон LONG

Given текущая цена внутри разрешенного диапазона, stop определен и лимиты не нарушены  
When приходит валидный LONG  
Then система формирует setup с общим риском не более 3%: первая risk-leg до 1,5% может войти около текущей цены, вторая risk-leg до 1,5% может быть разделена максимум на две лимитные заявки ниже; суммарный риск не растет.

### S-02 Stop under

Given сигнал содержит `стоп под 93050`  
When применяется утвержденное для стратегии правило offset  
Then итоговый stop строго ниже 93050; пример baseline — 92900. Если offset не определен однозначно, сигнал отклоняется.

### S-03 Безубыток

Given исполнены две цели  
When позиция остается открытой  
Then stop остатка переносится в рассчитанный breakeven с учетом комиссий и фактических fills, если такой перенос не ухудшает защиту.

### S-04 Повтор и re-entry

Given исходный signal уже обработан  
When Telegram повторно доставляет то же событие  
Then новый setup не создается.  
When автор явно пишет `сигнал активен` и ссылка на исходный сигнал разрешима  
Then создается новая revision с отдельным idempotency key после полной повторной risk-проверки.

### S-05 Ошибка внешней системы

Given ответ Bitget потерян, неполон или противоречив  
When статус ордера неизвестен  
Then новые заявки по setup блокируются, запускается reconciliation, а владельцу отправляется уведомление. Слепой retry создания заявки запрещен.

### S-06 DRY_RUN isolation

Given режим DRY_RUN  
When любой компонент пытается вызвать торговый endpoint  
Then вызов блокируется адаптером до сети, намерение записывается как simulated, тест завершается ошибкой при обходе защиты.

## 7. Risk and execution rules

Политика полностью определена в `governance/risk-policy.toml`. Основные параметры: риск до 3% на setup, две risk-legs по 1,5%, максимум 5 одновременных позиций, leverage 10–25, cross margin, обязательный stop, лимитные заявки, time stop 240 минут. Leverage не заменяет position sizing по расстоянию до stop.

Расчеты денег, цены, количества и комиссий выполняются decimal/fixed-point. Округление производится по инструментальным ограничениям, полученным из официального Bitget API и зафиксированным в тестовых fixtures.

## 8. State machines

Signal: `RECEIVED → PARSED → VALIDATED → APPROVED | REJECTED → ARCHIVED`.

Setup: `PLANNED → ARMED → PARTIALLY_FILLED → OPEN → REDUCING → CLOSED`; аварийные ветки `HALTED` и `RECONCILING`. Переход из `RECONCILING` разрешен только после подтвержденного снимка состояния биржи.

Order intent: `CREATED → SUBMITTING → ACKNOWLEDGED → PARTIALLY_FILLED → FILLED | CANCELLED | REJECTED | EXPIRED`. Неизвестный результат submission не возвращается в `CREATED`.

## 9. Non-functional requirements

- Перезапуск не создает дубликаты; состояние восстанавливается из durable journal.
- Все решения parser/risk/execution журналируются без секретов с correlation ID.
- Наблюдаемость: latency, parse reject rate, duplicate rate, order reject rate, reconciliation duration, realized/unrealized PnL и drawdown paper-портфеля.
- Kill switch блокирует новые заявки и пытается безопасно отменить ожидающие заявки; поведение открытых позиций задается отдельной подтвержденной командой.
- Конфигурация валидируется при старте; неизвестное поле или противоречие приводят к отказу запуска.
- Приватный Telegram UI отвечает только allowlist owner ID и не показывает секреты.

## 10. Research and backtest protocol

История двух каналов импортируется с исходными timestamp, reply-связями, edits и deletes. Replay воспроизводит состояние на момент события и не использует будущие сообщения или будущую цену. Backtest учитывает комиссию, funding, slippage, задержку, limit-fill model и пропуски данных. Train/tune, validation и holdout разделяются по времени; holdout не используется для настройки. Результат сравнивается минимум с no-trade и простым buy-and-hold/always-flat baseline там, где сравнение применимо.

Стратегия не допускается даже к limited live, пока не подтверждены корректность исполнения, устойчивость к реалистичным издержкам и paper-результаты на заранее определенном окне. Это фильтр допуска, а не обещание доходности.

## 12. Open decisions

- Точные numeric channel IDs и owner Telegram ID вносятся как secrets/config, не в Git.
- Технический offset stop должен быть формализован по направлению и волатильности до paper stage; baseline-пример 93050 → 92900 не является универсальным числом.
- Правило поведения открытой позиции при kill switch требует отдельного выбора владельца.
- Минимальная длительность и количественные пороги paper stage утверждаются до перехода из DRY_RUN.
